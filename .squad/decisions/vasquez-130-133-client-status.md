### 2026-09-03: D-189 (proposed) — #133 device edit Status control: no new ownership gating; backend default-status hole documented
**By:** Vasquez (via Copilot)
**What:** Added a Status control to the device edit form (`DeviceForm.svelte`) so `status` is always forwarded on submit — fixing the defect where omitted status caused `UpdateDeviceRequest.Status`'s C# default (`Active`) to silently reactivate/reset InRepair/Lent/Retired devices on any edit. Also preserves `retiredDate`/`disposalMethod` in the payload when the device's current status is Retired, since the backend's `EnsureRetiredDeviceMutationIsSafe` guard does a strict equality check on those fields (unlike the general status-change path, which falls back to the current value when omitted).
**Decision:** Did NOT add ownership-based restriction to the new edit-form Status control, even though the backend `UpdateDevice` endpoint uses `AuthorizationPolicies.AdminOrMember` with no per-device ownership check — unlike the frontend's existing `canRetireDevice`/`canUnretireDevice` helpers, which restrict Members to their own devices for the one-click retire/unretire quick actions.
**Why:** Inventing a new ownership restriction for this one field would be new authorization semantics beyond this issue's scope (task explicitly said to document backend follow-up rather than cross role boundaries silently). Instead, the Status control is wired through the existing generic `disabledFields` prop so any future/adjacent gating can reuse the established mechanism without a new bespoke pattern.
**Observed inconsistency (backend/product decision needed):** A Member can currently change *any* device's status via the edit form (no ownership check), while the quick-action retire/unretire buttons restrict Members to devices they own. This is a pre-existing authorization gap, not introduced by this fix, but now more directly reachable since the edit form's Status control makes status changes a first-class, always-visible action.
**Also flagged:** `UpdateDeviceRequest.Status` defaulting to `Active` on omission remains an unsafe hole for any *other* API caller (script, future mobile client, Swagger "Try it out") that doesn't set status explicitly — the frontend fix only protects requests routed through this form. Recommend backend either make `Status` required (no default) on `UpdateDeviceRequest`, or resolve a missing status server-side from existing device state instead of defaulting to `Active`.
**Related:** #133, PR #153
